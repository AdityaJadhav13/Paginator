**The independent verification** (2026-11-02, between the 03:49 runs and the fix pass, by a separate agent on stacks
of its own) reproduced the phone smoke 4 times (4 passed), the headers check (59/59) and the drill (11 PASS, the live
database unchanged by md5). It also found two blocking defects in the drill, fixed since, each with a unit test
(`apps/api/test/unit/restore-drill.test.ts`):
- a restored database's name that existed already made the drill fail and then **drop that database**; the drill now
  drops only a database it made, and its name has a random part, so two drills never pick the same one;
- a failed backup left the drill waiting for minutes with an idle session open; every session is now closed on every
  path, and the command exits at once (failure path 2 above).

### What the phone smoke goes through
All through the real screens and the real API, against Postgres 18.6, SeaweedFS 4.48 and Mailpit 1.31.6:
1. The Owner (made by `bootstrap-org`) opens the "confirm your address" and "choose a password" emails from Mailpit and
   sets a password.
2. The Owner turns on two-step sign-in in Account security, using the key the screen shows; the smoke computes the codes
   (RFC 6238). The backup codes are shown.
3. The Owner signs out with the app's own "Sign out" control, then signs in with the password and a code at `/mfa`.
   Just before, the smoke waits until the Owner's session answers steadily: for a few seconds after two-step is
   turned on it can answer 401 (L2-345).
4. The Owner invites a Reporter from Team. The Reporter opens the invitation email, makes an account, confirms the
   address from a second email, and joins. The Owner makes the edition of 1 December 2026 (8 pages) on the Editions
   screen ("Create edition").
5. The Reporter writes a story and attaches a photo, drawn by the browser as a 640 × 480 JPEG. The photo goes the whole
   way:
   - the browser uploads it straight to the store;
   - the API checks it and puts a job on the engine's queue;
   - the queue (`apps/engine-queue/src/main.ts`) runs the real Python runner, `pgn_worker.run`, with macOS's Generic
     CMYK profile (not the newsprint profile, which is private);
   - the API takes the result, and the photo is **ready**.

   The editor shows "640 × 480 pixels". The Reporter sends the story to the desk.
6. The Owner's stories list, open the whole time, says "This list has changed" without a reload (a live update). The
   Owner opens the story, picks it up, comments, and sends it back with a reason.
7. The Reporter's editor, also never reloaded, shows the comment and the status Draft (live updates). The Reporter
   changes the text and sends the story again.
8. The Owner picks it up, chooses the edition in the editor's Edition field (saved), and marks it **Ready**.
9. **Send to the Desk**, on the Editions screen: it shows "Stories: 1 · Ready: 1 · Spiked: 0"; the button downloads the
   ZIP in the browser and says "Stories downloaded: 1":
   - the ZIP holds exactly `bundle.json` and `photos/<sha256>.jpg`, whose SHA-256 is that of the file the Reporter's
     phone sent;
   - `bundle.json` has the format `pageinator.story-bundle/1`, the right organisation, publication and edition (date
     and 8 pages), and exactly the story keys of `tools/desk/CONTRACT.md` §6, with the changed body in desk-text/1;
   - the Desk's own code (`deskserver/bundle.py`, through `apps/api/test/support/desk_roundtrip.py`) opens the file
     and imports it into a throwaway Desk home: one article is added with that text and a 640 × 480 photo.
10. Neither browser threw an error or logged a console error, and no request was answered with a 5xx. The only console
    errors allowed are the browser's own "Failed to load resource … 4xx" lines.

- **The migrations check** compares the restored database with the live one and with the migrations folder the release
  carries (none pending, none unknown), so it needs no count kept by hand.
- **The photo check:** with `PGN_S3_WORK_BUCKET` unset it is SKIP; with a bucket the key cannot read, or one without the
  originals, it is FAIL (failure path 1).
- **Restored databases:** after every run, none remained.
- **Dumps stay:** each run that gets past the backup writes **one new dump to the backups bucket, under the 35-day
  GOVERNANCE lock**, as a nightly one. Failure path 1 left one too. After these runs the scratch bucket held 5, locked
  until 2026-12-06; the stack and its buckets were then removed. In the pilot, each drill adds one locked dump.
- **"Unchanged" is per table:** a whole-database `pg_dump` md5 differs between two dumps with nothing changed (row order),
  so the check was an md5 of each table's rows.
- **The account for the cookie checks:** pilot-local has no mail server, so the fictional Owner's password and
  confirmed address were set in the database. The password was hashed with the app's own `hashPassword`. Two-step was
  turned on afterwards through the real routes, for the data the drill restores.

### Headers check (pilot-local), what the 59 lines cover
- The app's `/`, `/stories` and a missing asset: CSP, HSTS for a year, nosniff, frame-deny, COOP/CORP and no-referrer;
  a missing asset is a 404 with no-store.
- The API's `/api/v1/me` and sign-in: no-store, and the API's own CSP.
- The session cookie `__Secure-pgn.session_token`: HttpOnly, Secure, SameSite=Lax, 12 hours.
- 10 forms of the health paths are not routed through Caddy.
- TLS 1.3 is used, and TLS 1.1 is refused.

## Found by the smoke, and since built

The first smoke run (02:47) found no way in the web app to make an edition, to put a story in one, or to "Send to the
Desk": it had to make the edition in SQL and use the API directly. These were built and merged (feat/l2-editions
90e4289: `GET`/`POST …/pubs/:p/editions`, the Editions screen, the editor's Edition field), and the smoke now does all
three through the screens, with no SQL or direct API call (it reads the story through the API only to wait for the
photo to be ready). The same merge removed the "Simulated" status note in the workspace header (L2-340, closed).

## What L2.1 still lacks (against 09 §4 and 10 §1)

- **Hosting:** the pilot is not hosted. TLS, managed Postgres with point-in-time recovery, S3, email, nightly backups and
  the uptime alert have run only as pilot-local or as tests (`docs/runbooks/deploy.md`); none of it on AWS.
- **"Done when" items 1, 4 (on a new instance, and path A) and 5**, as in the table above.
- **The release check:** real staff data may go in only after items 2–4 are true; item 4 is true on pilot-local only.

## Not verified

- **Real AWS:** RDS point-in-time recovery, the nightly dump on real S3 under Object Lock, a restore into a new RDS
  instance, IAM, CloudWatch alarms and the uptime check.
  - On RDS, the drill's admin must be allowed to create a database and restore `pgn_owner`'s objects; this is untested.
  - In the pilot, the backup's S3 key cannot read the work bucket. The photo check is then SKIP, unless another key is
    used.
- **The real host:** that containers cannot reach the instance metadata service (IMDS hop limit 1;
  `docs/runbooks/deploy.md`). Pilot-local has no metadata service.
- **Real out-of-memory:** the engine worker killed by the kernel's OOM killer on the 1 GB container. Only its handling
  in code is tested.
- **The headers check against the real domain** (D-2), over the internet, with a real certificate.
- **Real email delivery** (SMTP with TLS to a real provider). Only Mailpit was used.
- **The real newsprint colour profile, and colour parity.** The smoke used macOS's Generic CMYK profile.
- **The phone smoke in CI.** It ran on a developer's Mac only (L2-341), in Chromium only, with emulated phone
  viewports, not real phones or Safari.
- **A native Marathi review of any screen** (D-5). The smoke ran in English.
- **The owner's open decisions:**
  - D-2: the domain and the email sender;
  - D-5: the Marathi review;
  - D-6: the staff privacy notice and the legal pages;
  - D-8: pikepdf;
  - D-9: the WAN-IFRA profile;
  - D-10: photo retention, and GPS/EXIF in originals;
  - PITR days, alert recipients and a standby database;
  - the Playwright browser licences;
  - whether a failed photo's original should go to the Desk (L2-334).
